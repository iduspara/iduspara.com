When an agent gets poor context, it produces confident but messy code. With good context, a side project feels like it has a small team. When I maintain a bilingual Next site and several products alone, what I put around the model matters as much as which model I use.

## What "context" means here

For me it is the combination of repo layout, naming conventions, forbidden patterns, and short instructions agents actually read, plus the brief I type for each task.

This repo has an `AGENTS.md` at the root for a reason: Next.js 16 changed a lot of APIs, and the models' training data is out of date. The file is short and blunt, and it points the agent at the docs that ship with the installed version:

```md title="AGENTS.md"
## This is NOT the Next.js you know

This version has breaking changes — APIs, conventions, and file structure may all
differ from your training data. Read the relevant guide in `node_modules/next/dist/docs/`
before writing any code. Heed deprecation notices.
```

That one paragraph prevents a whole class of mistakes: `middleware.ts` instead of `proxy.ts`, an i18n library where `next/root-params` already does the job, or a confident rewrite into last year's App Router.

The rest of the house rules are cheap to state and expensive to rediscover after a "helpful" rewrite: content is MDX with Zod-validated frontmatter, UI is Server Components by default, dictionaries are server-only JSON.

## Briefing patterns that work

I state the goal, the constraints, and what not to touch. One job per session beats a vague "improve the site". A typical brief looks like this:

```md
Goal: add a "Latest posts" section to the homepage.

Constraints:
- Reuse `Section` and `PostList`. No new list or card component.
- Server Component only. No client state, no "use client".
- Copy goes into both `messages/en.json` and `messages/de.json`.

Out of scope: the i18n helpers, the header, anything in `lib/seo.ts`.
Done when: `pnpm typecheck`, `pnpm lint` and `pnpm build` pass.
```

When the task spans layers, I say which layer is in scope: content, UI or config. Mixing all three in one prompt is how unrelated files get "cleaned up".

## Fighting rot

Small diffs, typed boundaries and a build that fails on bad input keep agents on track. Frontmatter is the clearest example. Every post and case study goes through a Zod schema, and a mistake stops the build with a message that names the file and the field:

```ts title="lib/content.ts"
function parse<T extends z.ZodType>(schema: T, data: unknown, file: string): z.infer<T> {
  const result = schema.safeParse(data);
  if (!result.success) {
    throw new Error(`Invalid frontmatter in content/${file}:\n${z.prettifyError(result.error)}`);
  }
  return result.data;
}
```

```txt
Invalid frontmatter in content/blog/en/my-post.mdx:
✖ Too big: expected string to have <=160 characters
  → at description
```

An agent can read that and fix it on its own. That's what I want: the repo gives feedback without me having to step in.

I still review before merge, the same way I would review a colleague. If the agent drifted, I revert and tighten the brief instead of patching a pile of drive-by edits.

## Multi-repo reality

This site, [MiniRemote](/en/portfolio/miniremote), [CupertinoUI](/en/portfolio/cupertino-ui) and [Shadcn Builder](/en/portfolio/shadcn-builder) do not share one monorepo. Each has its own conventions and its own agent notes. I don't assume an agent remembers MiniRemote's MCP rules while editing a portfolio MDX file. A fresh session per repo works better than one long chat across products.

## Docs vs the prompt

Stable rules belong in the repository: structure, lint config, "read Next's local docs". Task-specific intent belongs in the prompt. Pasting a style guide into every message wastes the context window. Forgetting to say "don't touch X" can cost an afternoon.

When you work alone, this setup is worth the time. You write it once, and every agent session starts with the standards you would enforce yourself.
